# SKILL 文件书写规范（Skill Style Guide）

本文件定义单个 `SKILL.md` 的结构与格式规范。

本规范引用并依赖以下子规范（冲突时本文件优先）：
- [约束书写规范](references/constraint.md) — 约束表格格式、编号、措辞要求
- [编号规范](references/numbering.md) — 流程步骤的层级编号规则
- [文档组织与写法规范](references/organization.md) — 目录结构、渐进式披露、链接基准、检查对象范围、示例书写与条目可判定性

## 规则

### 1. Frontmatter

每个 `SKILL.md` 必须以 YAML frontmatter 开头（`---` 包裹），包含以下字段：

```yaml
---
name: skill-name
description: 一句话描述技能用途。Use when 触发场景的自然语言描述。
triggers:
  - 触发关键词 1
  - 触发关键词 2
inputArgs: [arg1, arg2]
---
```

字段分三类，**未在下列三表中出现的字段一律不得新增**。

**官方必填字段**（Claude Code 本体识别，缺失则技能无法被正确加载或路由）：

| 字段 | 类型 | 说明 |
|------|------|------|
| `name` | string | 技能唯一标识，仅小写字母/数字/连字符（kebab-case），匹配 `^[a-z0-9-]{1,64}$`，必须与技能目录名逐字一致 |
| `description` | string | ≤1024 字符，格式为「做什么。Use when 触发场景」——`Use when` 之前写能力，之后写触发条件，两侧均不得为空 |

**官方可选字段**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `allowed-tools` | string[] | 限制本技能可用工具；声明与判定要求见 [1.1](#11-allowed-tools-声明要求) |
| `license` / `metadata` | string / map | 分发元信息，不影响加载 |

**编排扩展字段**（本规范约定，Claude Code 本体会忽略，由外部编排器消费；无编排器时可整体省略）：

| 字段 | 类型 | 说明 |
|------|------|------|
| `triggers` | string[] | 触发关键词列表，至少 1 项，每项为用户可能说的自然语言短语 |
| `inputArgs` | string[] | 输入参数名列表，必须与正文 `## 参数` 表格的参数名双向完全一致 |
| `consumes.stages` | string[] | 适用的编排阶段 |
| `consumes.actionTypes` | string[] | 消费的动作类型 |

**description 写法要求**：

- `Use when` 之后必须写用户可能的**真实说法或场景**，严禁用技能名自我指代（反例：`Use when 用户需要 xx-check 检查` —— 用户不知道这个词就永远触发不了）
- 触发场景应足够具体以与同仓库其他技能区分，严禁使用「代码审查」「文档检查」这类会与多个技能撞车的宽泛表述
- 存在明确不适用场景时，在 `Use when` 之后补一句 not-when（如「纯事实查询时不要使用」）

#### 1.1 allowed-tools 声明要求

**只读型技能判定**：取 `description` 中 `Use when` 之前的能力描述部分，命中下列只读型词表中的任一词 → 判定为只读型技能；无命中 → 判定为非只读型技能。**严禁**用词表之外的任何主观归类作为判定手段。

```text
只读型词表：检查 审查 校验 排查 诊断 查询 分析 调研 统计
工具名封闭清单：Read Grep Glob Bash Write Edit NotebookEdit WebFetch WebSearch Task
写入类封闭清单：Write Edit NotebookEdit
否定词封闭表：不调用 不使用 不得 无需 严禁 禁止
```

- 只读型技能**必须**声明 `allowed-tools`，字段缺失即违规
- 只读型技能的 `allowed-tools` **严禁**出现写入类封闭清单中的任一工具名，出现即违规（唯一例外见下方「落盘例外」）
- 非只读型技能的 `allowed-tools` 为可选字段，未声明不违规
- 已声明 `allowed-tools` 时，其每一项**必须**逐字属于工具名封闭清单，出现清单外的字符串即违规
- 正文出现下列任一形态时，`allowed-tools` **必须**含 `Bash`，缺失即违规：`scripts/` 路径的调用行；反引号内以 `git`、`grep`、`find`、`sed`、`awk`、`sh`、`bash`、`python`、`node` 起首的命令串
- 已声明 `allowed-tools` 时，正文中出现的工具名封闭清单里的每一个字符串**必须**同为 `allowed-tools` 的一项。命中范围只限描述本技能自身执行动作的语句：以 `。`、`；`、`\n` 为句边界切句，工具名所在句中出现否定词封闭表里的任一词时不计命中（如「本技能不调用 `Write`」不计）

**落盘例外**：仅在下列两个条件全部成立时，只读型技能的 `allowed-tools` 允许含 `Write`。

1. `### 产物文件` 表中至少存在 1 行产物
2. 该产物行「路径」列中出现的每个 `{占位符}` 名均已在 `## 参数` 表中声明

两条件缺任一 → 按「只读型技能严禁出现写入类工具」判违规。本例外只放开 `Write`；`Edit` 与 `NotebookEdit` 出现在只读型技能的 `allowed-tools` 中一律违规，无例外分支。

### 2. 路径解析基准声明

每个 `SKILL.md` 必须在一级标题（`# 标题`）**紧随其后的第一个非空块**放置以下 `> [!IMPORTANT]` callout，措辞逐字匹配，不得改写或扩写。三者顺序固定为 frontmatter → 一级标题 → 本 callout，之间只允许空行：

```markdown
> [!IMPORTANT] 路径解析基准
> 文档内相对路径引用一律以本 skill 根目录（`SKILL.md` 所在目录）为基准解析。
```

### 3. 约束章节

SKILL 文件中的约束章节必须遵循 [constraint.md](references/constraint.md) 定义的全部规则，并满足以下补充要求：

**总纲声明**（可选）：当 Skill 有一条贯穿性核心精神时，在约束表格上方用引用块声明：

```markdown
## 公共约束

> [强约束] 总纲：只搬运、只标注、不改写、不发散。

（此处紧接约束表格，其列结构见 constraint.md 规则 2）
```

- 总纲位置固定在约束表格上方，不替代表格中的具体约束
- 非必须 — 若 Skill 无明显的贯穿性精神则省略

**内联 `[强约束]` 引用块**：当流程步骤中存在执行红线时，可在对应 STEP 标题下方就近声明：

```markdown
> [强约束] STEP 10 执行红线（违反任意一条 = 严重事故）
>
> 1. ...
> 2. ...
```

- 仅用于流程步骤内的就近强调，不替代 `## 公共约束` 章节
- 管辖单个 STEP 的内联强约束，位置**必须**紧随该 STEP 标题
- 管辖两个及以上连续 STEP 的内联强约束，位置**必须**置于 `## 核心流程` 标题正下方，并在约束正文中显式写出管辖范围（如「STEP 3~7」）；未写明管辖范围的一律按上一条判违规

**判定依据映射**：约束章节需检查的方面与其判定依据的对应关系如下。判定内容一律回落 constraint.md 原文，本节不复述。

| 检查项 | 依据 |
|--------|------|
| 约束章节标题 | [constraint.md 规则 1](references/constraint.md#1-约束章节标题) |
| 约束表格列结构 | [constraint.md 规则 2](references/constraint.md#2-约束表格格式) |
| 约束编号格式 | [constraint.md 规则 3](references/constraint.md#3-编号格式) |
| 约束描述书写要求 | [constraint.md 规则 4](references/constraint.md#4-约束描述书写要求) |
| 约束描述强调标记 | [constraint.md 规则 6](references/constraint.md#6-强调标记) |
| 违反后处理列写法 | [constraint.md 规则 5](references/constraint.md#5-违反后处理列) |
| 引用块约束（总纲 / 内联）的编号与用途 | [constraint.md 规则 7](references/constraint.md#7-引用块约束补充格式) |

### 4. 输出规范章节

每个 `SKILL.md` 必须包含 `## 输出规范` 章节：

#### 4.1 产物文件（`### 产物文件`）

表格固定 3 列：

```markdown
### 产物文件

| 文件 | 条件 | 路径 |
|------|------|------|
| 分析报告 | 必产 | `{outputDir}/report-{taskId}.md` |
| 附加明细 | 仅 `mode=full` | `{outputDir}/detail-{taskId}.md` |
```

- **文件**：产物名称
- **条件**：何时产出（`必产` / `mode=full` / `exitCode=3 时` 等）
- **路径**：产物路径模板

产物路径含由输入拼接而成的文件名片段时，必须在本章节或对应 STEP 用 `> [强约束]` 声明该片段的生成规则（字符白名单、大小写、长度上限与计数单位、为空时的回退值），**严禁**将用户输入原文直接拼入文件名。落盘完成后必须在输出中回显产物的绝对路径。

#### 4.2 退出码（`### 退出码`）

表格固定 4 列：

```markdown
### 退出码

| exitCode | 含义 | 触发场景 | 后续动作 |
|---------|------|---------|-----------|
| 0 | 完成 | 全部产物写入成功 | 读取产物 → 推进流程 |
| 1 | 执行失败（可重试） | 网络超时、编译失败 | 询问用户：重试 / 终止 |
| 2 | 输入异常（不可重试） | 必填参数缺失、文件不存在 | 走 ask 决策 |
```

- 4 列均为必填
- exitCode 值域：`0`（成功）、`1`（可重试）、`2`（不可重试）、`3`（需人工决策）
- `触发场景` 列必须汇总该 exitCode 对应的**全部**错误类别，流程正文中出现的每一处 `→ stderr + exitCode=N` 都必须能在表中找到对应场景
- **例外**：检查/审查类 Skill 可将 `1` 定义为「检查完成，存在违规」，此时必须在 `含义` 列写明，不得与「可重试」混用
- **例外**：由 Claude 在对话中直接执行、无外部进程返回退出码的 Skill，必须在本表上方声明「每次结束时在输出末尾单独打印一行 `状态：{含义}（exitCode={N}）`」，使退出码有可观测落点。触发条件的客观判据：正文中既无 `scripts/` 路径的调用行，也无 [1.1](#11-allowed-tools-声明要求) 所列反引号命令串形态；是否落盘产出文档不作为本例外的判据

#### 4.3 stderr 格式（`### stderr 格式（JSONL，单行）`）

```markdown
### stderr 格式（JSONL，单行）

\```jsonl
{"message":"...","detail":"...","hint":"..."}
\```

字段约束：
- `message` 必填，自由文本，简洁单行
- `detail` 可选，多行文本（保留原始错误信息）
- `hint` 可选，给用户的修复提示
```

### 5. 参数校验步骤

每个 `SKILL.md` 的核心流程第一个 STEP 必须为参数校验步骤（`### STEP 0：参数校验` 或 `### STEP 1：参数校验`）。

**边界原则**：参数校验只判断入参本身是否合法，**严禁**出现读取文件内容、解析文档、调用脚本、查询数据、推断业务结论等动作。此类动作必须放在后续 STEP。

**声明式写法**：该 STEP 正文只允许包含两种内容——`- **{行标签}**：{参数名列表}` 形态的列表行，以及一行收尾的 `任一校验失败 → stderr + exitCode=2`。**严禁**展开为 STEP 子步骤或写成散文段落。

**交互式必填参数的例外**：若某必填参数缺失时的正确处理是**向用户提问**而非报错退出（如对话类 Skill 的分析主题），必须在该行显式写明「缺失时不得报错退出，必须先向用户提问」，并在退出码表中排除该参数。

**标准校验顺序**（从快到慢）：

| 行标签 | 校验内容 | 说明 |
|--------|---------|------|
| **必填** | 参数存在性 | 批量列出所有必填参数名 |
| **格式** | 正则/格式校验 | 如 taskId 正则（可选行） |
| **枚举** | 枚举值合法性 | 列出参数名 + 合法值 |
| **文件** | 文件存在性 | 列出需校验的文件参数 |
| **目录** | 目录存在性 | 通常为 `projectPath` |
| **创建** | 目录不存在则创建 | 通常为 `outputDir` |
| **条件** | 条件参数校验 | 如 `round > 1` 时的额外参数（可选行） |

无对应校验项的行省略不写。

**格式模板**：

```markdown
### STEP 1：参数校验

按标准校验顺序校验：
- **必填**：`taskId`、`mode`、`projectPath`、`outputDir`
- **格式**：`taskId`（匹配 `^[A-Za-z0-9_-]+$`）
- **枚举**：`mode`（`quick` / `full`）
- **文件**：`inputDoc`
- **目录**：`projectPath`
- **创建**：`outputDir`
- **条件**：若 `extraDoc` 非空，校验文件存在

任一校验失败 → stderr + exitCode=2
```

### 6. 错误信息承载规则

**禁止独立的 `## 错误处理` 章节**。错误信息由以下三处覆盖：

| 承载位置 | 职责 |
|---------|------|
| 退出码表格 `触发场景` 列 | 汇总每个 exitCode 对应的错误类别 |
| `### stderr 格式` 章节 | 定义 JSONL schema（message/detail/hint） |
| 流程步骤正文 | 具体分支的 stderr 输出内容（`→ stderr + exitCode=N`） |

**例外**：若 Skill 有独立于 exitCode 的错误码体系（如自定义 `errorType`），可保留 `## 错误类型` 章节单独描述。

### 7. 流程步骤编号

SKILL 文件中的流程步骤必须遵循 [numbering.md](references/numbering.md) 定义的层级规则。

### 8. 危险信号与反合理化章节

每个 `SKILL.md` 必须包含以下两个章节，位于核心流程之后：

#### 8.1 危险信号（`## 危险信号（Red Flags）`）

列出可观测的执行偏差信号，出现任一项必须回退修正。

```markdown
## 危险信号（Red Flags）

以下可观测信号表明执行出现偏差，出现任一项必须回退修正：

- RF-EX1: 产出文档中的段落措辞与原文对比存在用词替换
- RF-EX2: scope 边界模糊的段落被跳过而非保留
```

**格式要求**：
- 章节标题必须为 `## 危险信号（Red Flags）`，逐字匹配
- 每条使用无序列表 `- ` 格式
- 编号前缀为 `RF-` + 关联约束编号（如约束 `EX1` 对应 `RF-EX1`），同一约束有多条 Red Flag 时追加字母后缀（如 `RF-EX1a`、`RF-EX1b`）
- 至少包含 1 条

#### 8.2 反合理化（`## 反合理化（Anti-Rationalization）`）

预设 Agent 可能用来合理化违规行为的借口，并给出对应反驳。

```markdown
## 反合理化（Anti-Rationalization）

| 借口 | 反驳 |
|------|------|
| "原文措辞不清晰，我调整后对下游更友好" | 你是搬运工不是编辑。原文错误由下游处理。 |
```

**格式要求**：
- 章节标题必须为 `## 反合理化（Anti-Rationalization）`，逐字匹配
- 使用两列表格：`借口` / `反驳`
- 借口列使用引号包裹的第一人称陈述
- 反驳列为简洁有力的驳斥
- 至少包含 1 行
