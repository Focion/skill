# 指令书写准则（Karpathy）

本文件面向**指令书写者**，讲"怎么下指令能让 Agent 跑更长 loop / 拿更大杠杆"。与姊妹文档 [guidelines.md](references/guidelines.md) 互补：本文约束指令书写者的写法，guidelines.md 约束 Agent 的行为。

> **引用身份区分：** 本文件作为**执行准则**时偏向"投入指令设计成本，换 agent 自治时间"，一次性小改动用命令式直说反而更快；作为**检查依据**时逐条适用，**严禁**以"任务琐碎""场景简单"为由跳过判定或将违规降格为提示。

---

## 核心观点

指令的形态决定 agent 能跑多长的 loop——声明式（给成功标准）优于命令式（给步骤）。

| 维度 | 命令式（弱杠杆） | 声明式（强杠杆） |
|------|------------------|------------------|
| 你告诉 agent | **怎么做** | **做到什么算成功** |
| 卡住时 | 每步都要你介入 | agent 自己循环到达成 |
| 你的时间 | ≈ agent 的步数 | ≈ agent 的轮次 |
| 适合 | 一次性小改动 | 有可验证标准的任务 |

---

## 1. 给成功标准，不给步骤

把"我要 X"翻译成"什么样的检查通过等价于 X 做完了"，再让 agent 在循环里追赶。

```
❌ "读取 config.json，解析 timeout 字段，如果大于 30 就写日志告警，然后……"
✅ "写一个测试：当 config.json 里 timeout > 30s 时触发 WARN 日志；让它通过。"
```

**判断标准**：能写成「执行 `xxx`，期望输出 `yyy`」就用声明式；对超出一次性小改动的任务，只能写成「先做 A 再做 B 再做 C」说明你自己也没想清楚什么算"做完了"。

适用场景：

| 任务 | 命令式（弱） | 声明式（强） |
|------|-------------|-------------|
| bug 修复 | "在第 N 行加 nil 判断" | "写复现 bug 的测试，让它通过" |
| 重构 | "把方法 A 拆成 B 和 C" | "保持现有测试通过，把模块 X 拆成 X1+X2" |
| 性能优化 | "把循环改成并发" | "保持测试通过，让 benchmark Y 提升 30%" |
| 新功能 | "先建表再写 handler 再加路由" | "实现 spec [描述]；通过测试用例 [列表]" |

---

## 2. 先朴素正确版，再优化

```
❌ 一上来就要："写一个 LRU + bloom filter 的高性能去重器。"
✅ 两步走：
   1. "先写最朴素的去重器（O(n²) set 查重就行），跑通测试。"
   2. "保持测试全部通过，把它优化到 O(n)。"
```

**原因**：
- 朴素版提供正确性锚点。
- agent 在「保持测试通过」的强约束下做优化，等价于把"正确 + 快"拆成"正确" → "快"，每步都可验证。
- 一次到位的复杂实现错了，你很难定位是设计错还是实现错。

适用场景：性能敏感代码 / 算法优化 / 涉及缓存或并发的重构 / 需要复杂数据结构的实现。

---

## 3. 写测试先行，把审查重心从实现移到测试

工作模式：

1. 你写或让 agent 写**测试**（描述期望行为，允许失败）。
2. agent 实现代码直到测试通过。
3. **你审查测试本身**是否真的描述了你要的行为。

这把审查从"读 1000 行实现"转移到"读 50 行测试"。人脑判断"测试是否描述了对的东西"，比判断"实现是否正确"容易得多。

**注意**：测试本身也可能被 agent 写错（测错的东西）。你的关注重心从代码移到测试——但**关注重心不消失**。

---

## 4. 让 agent 自己进 loop

声明式指令的真正威力，在于把 agent 放进一个**自我验证 → 自我修正**的循环里。常见 loop 形态：

| Loop 类型 | 输入 | 验证信号 |
|----------|------|---------|
| 测试驱动 | 写好的测试 | `go test` 退出码 |
| 编译驱动 | "保持 `make build` 通过" | 编译器退出码 |
| 评分驱动 | "让评分工具 A 区得分 ≥ 45" | 评分输出 |
| 浏览器驱动 | 配上 browser MCP | 页面截图 / DOM 断言 |
| Lint 驱动 | "通过所有 lint 规则" | linter 输出 |
| 契约驱动 | "通过契约测试脚本" | 契约 bash 退出码 |

**关键约束**：验证信号必须是**机器可读的退出码 / 数值 / 布尔**，不能是"看起来对就行"。

---

## 5. 反模式

| 反模式 | 为什么不好 |
|--------|-----------|
| 一长串"先做 X 再做 Y 再做 Z" | 每步出错你都要介入，agent 没法独立 loop |
| 让 agent 实现复杂方案，没有可执行验证标准 | "看起来对就行" → 你被迫一行行读代码 |
| 测试先写，但你从不审查测试本身 | agent 测错的东西也能"全绿"，错觉式通过 |
| 把可量化的标准写成模糊中文 | "性能要好" 换成 "benchmark Y 提升 30%" 才能进 loop |
| 跳过朴素版直接要终极版 | 错了无法定位是设计错还是实现错 |
| Loop 的边界条件留模糊（"差不多就行"） | agent 要么死循环要么早退，全凭运气 |

---

## 一句话总结

**指令的形态决定杠杆的长度。给 agent 一个目标和一个机器可读的验证信号，而不是一份步骤说明书。**
