# 技术方案段（Blueprint Tech）

> [!IMPORTANT] 路径解析基准
> 文档内相对路径引用一律以本 skill 根目录（`SKILL.md` 所在目录）为基准解析。

本段是 blueprint 流水线的**技术段**，出手序为 3：把「它能不能被做出来、代价多大」逼到可算，产出技术分册与台账里的 `TEC` 分区。技术边界会直接砍掉一部分商业空间，故紧随商业段之后。本段的功能项估时与依赖费用是裁决段工时与现金需求算式的输入。本段**只**闭环字段与登记事实，否决判定与结论态一律交裁决段。提问轮次不设上限，也不向用户宣告。

## 适用与不适用

- ✅ **适用**：用户已有一个可点名的产物形态，且愿意逐轮回应提问 —— 功能边界划定、选型取舍、难点验证设计、依赖与许可核对。
- ❌ **不适用**：纯事实查询、单点执行任务、已有完整技术方案只要求评审 —— 直接回答，**严禁**启动本流程。
- 🚫 **不受理**：诉求的成立以违反法律法规、侵犯他人权益或规避平台风控为必要条件 —— 说明原因后停止，**严禁**输出方案（→ stderr + exitCode=2）。

## 参数

| 参数 | 必填 | 说明 |
|------|------|------|
| `demand` | 是 | 待展开的原始诉求（自然语言，可以只有一句话） |
| `slug` | 否 | 产物文件名片段，缺省 `idea`；由编排段生成并透传 |
| `outputDir` | 否 | 分册与字段台账的输出目录，缺省取当前工作目录 |
| `scope` | 否 | 档位，缺省 `full`；`screen` 时字段子集见 [fields.md 第四节](references/fields.md#四上游锚点与档位子集) |

## 公共约束

> [强约束] 总纲：先替用户把可能性摊开，再逐字段逼到可算。不替用户拍板，不拿臆测充事实，不以轮次收尾，不越过裁决段给结论。

| # | 约束 | 违反后处理 |
|---|------|-----------|
| IBT1 | 开始追问前**必须**完整读取 [fields.md](references/fields.md)，**严禁**凭 SKILL.md 摘要或记忆提问 | 停止本轮，先完整读取该文件 |
| IBT2 | 单轮需用户回答的问题数**必须**不超过 3 个，**严禁**单轮抛出 4 个及以上问题 | 超出的问题移入下一轮后重发本轮 |
| IBT3 | 每个问题**必须**按 [co-create.md 第二节](references/co-create.md#二单轮提问的候选生成规则)附模型先行给出的候选答案，**严禁**抛出无候选的开放式问题 | 补齐候选后重发本轮 |
| IBT4 | 每轮输出**必须**含至少 1 条用户未提过的发散点并标注 [co-create.md 8.1](references/co-create.md#81-手法表)的手法编号，**严禁**把本轮写成纯提问清单 | 补一条带编号的发散点后重发本轮 |
| IBT5 | 本段追问**必须**只覆盖 fields.md 第一节所载字段，**严禁**追问其他段前缀的字段 | 撤回越界问题，本轮只保留本段字段 |
| IBT6 | 用户给出的每个数值**必须**问明来路并按 [co-create.md 第五节](references/co-create.md#五来源等级)标出来源等级，**严禁**把口述数值直接记为已确认事实 | 补问来路后改标来源等级 |
| IBT7 | [fields.md 第三节](references/fields.md#三本段必核字段)所列字段**必须**联网取证并记录出处与取证日期，**严禁**以模型记忆中的价目与许可条款充当取证结果 | 停止该字段判定，先联网取证 |
| IBT8 | 未闭环的字段**必须**标为【缺口】并进入缺口清单，**严禁**用模型臆测值冒充用户已确认的事实 | 改标【缺口】并移入缺口清单 |
| IBT9 | 由模型代填的取值**必须**逐条标注【模型假设】，**严禁**与用户已确认事实混排 | 逐条补标来源标签 |
| IBT10 | 每轮的处置分类、取证与发散点**必须**按 [co-create.md 第十节](references/co-create.md#十分册与字段台账的就地更新)就地写入分册与字段台账，**严禁**把本轮结论只留在对话里 | 补写本轮更新后再抛下一轮 |
| IBT11 | 每轮输出**必须**给出本段完整度进度，**严禁**出现提问轮次的编号、上限或剩余次数 | 删除轮次表述，改回完整度进度 |
| IBT12 | 否决判定与结论态**必须**交由裁决段执行，**严禁**在本段输出否决结论或结论态 | 删除该结论，改为登记事实 |
| IBT13 | 本段取值与台账 `RQ5` 某条硬约束直接冲突时**必须**当场把冲突两端的取值摆给用户，**严禁**只写入分册而不告知 | 立即停止本轮，回读该冲突 |
| IBT14 | 台账缺产品分区时**必须**按 [fields.md 第四节](references/fields.md#四上游锚点与档位子集)把上游字段标为【缺口】并在分册声明未锚定，**严禁**凭模型代填的产品方案往下算 | 补标【缺口】并补写声明行 |
| IBT15 | `TEC1` 的每个功能项**必须**写出它对应的产品条目名，**严禁**留空该对应关系 | 补齐对应条目名后重写该行 |

## 核心流程

> [强约束] STEP 3~6 任一交互步骤中，用户主动叫停，或用户明确拒绝继续回应提问 → stderr + exitCode=1；`scope=screen` 时 STEP 5 的字段范围一律按 [fields.md 第四节](references/fields.md#四上游锚点与档位子集)执行，**严禁**按 `full` 档的全集推进。

### STEP 1：参数校验

按标准校验顺序校验：
- **必填**：`demand`（缺失时不得报错退出，必须先向用户提问「你想把哪件事的技术面理清楚？」，拿到回答后再进入下一步）
- **格式**：`slug`（匹配 `^[a-z0-9一-鿿-]{1,30}$`）
- **枚举**：`scope`（`screen` / `full`）
- **创建**：`outputDir`

任一校验失败 → stderr + exitCode=2

### STEP 2：读取本段规范

用 Read 工具完整读取 `references/co-create.md`、`references/fields.md`、`references/output-spec.md`，读完再进入下一步（遵循 IBT1）。

### STEP 3：读取或建立字段台账

读取 `{outputDir}/blueprint-{slug}.fields.json`；文件不存在时按 [fields.md 第四节](references/fields.md#四上游锚点与档位子集)新建并追问该节所列还原字段后写入。按该节逐项读取上游锚点取值，缺产品分区时按该节标注并声明（遵循 IBT14）。

### STEP 4：建立分册骨架

按 [output-spec.md 第一节](references/output-spec.md#一分册骨架)建立分册，未闭环的节写占位串，再单独一行回显分册绝对路径。

### STEP 5：逐字段发散、追问与取证

按 fields.md 第一节的字段次序轮转，输出逐字采用 [co-create.md 第九节](references/co-create.md#九单轮输出格式)的五行格式（遵循 IBT2、IBT3、IBT5、IBT11）：

- 本轮的待闭环字段与追问句式取 fields.md 第一节，用户回答命中第二节任一空洞回答时发出对应追加问法；发散点按 co-create 8.1 选手法、8.2 取首选手法，合规判据见 8.3（遵循 IBT4）
- 用户给出数值时按 co-create 第七节问明来路并标来源等级（遵循 IBT6），与既有取值冲突按 7.1 回读；fields.md 第三节的必核字段用 WebSearch 与 WebFetch 取证并按 co-create 第六节记录出处与日期（遵循 IBT7）；用户答「不知道」「你定」时按 co-create 第三节分类（遵循 IBT8、IBT9），单字段处置上限见第四节，**严禁**向用户宣告该上限
- `TEC1` 按 [output-spec.md 第二节](references/output-spec.md#二方案节模板)逐条写出对应的产品条目名（遵循 IBT15），切片某一步的条目既不在产品清单也不在本段功能项内时按 fields.md 第四节标出并交裁决段；本轮取值与 `RQ5` 硬约束直接冲突时当场回读（遵循 IBT13），否决判定一律留给裁决段（遵循 IBT12）；本轮分类给出后按 co-create 第十节更新分册与台账、写出 `文档：已更新 {节名列表}` 行，再抛下一轮（遵循 IBT10）
- 关键前提需用户之外的角色或系统才能确定、本次对话内无法闭环 → stderr + exitCode=3

### STEP 6：补齐台账与交回

全部字段完成判定后按 [output-spec.md 第四节](references/output-spec.md#四字段台账的写入范围)补齐台账，再输出段交回信号：`段交回`、`未闭环`、`分册` 三行。

## 输出规范

### 产物文件

| 文件 | 条件 | 路径 |
|------|------|------|
| 技术分册 | 必产，STEP 4 建立并逐轮更新 | `{outputDir}/blueprint-{slug}-tec.md` |
| 字段台账 | 必产，不存在时由本段建立并逐轮追加 | `{outputDir}/blueprint-{slug}.fields.json` |
| 对话内段交回信号 | 必产 | 直接输出到对话 |

> [强约束] `{slug}` 由编排段生成并透传，本段**必须**按 STEP 1 的格式校验逐字取用该参数值，**严禁**将 `demand` 原文拼入文件名，**严禁**在本段另行改写 `{slug}`。

```markdown
<!-- ✅ 正确：逐字取用透传的 slug -->
slug=做一个-roguelike-小游戏 → blueprint-做一个-roguelike-小游戏-tec.md
<!-- ❌ 错误：把 demand 原文拼入，空格与全角括号进入文件名，产出跨平台不可用的路径 -->
blueprint-做一个 Roguelike 小游戏（手机端）-tec.md
```

### 退出码

本技能在对话模式下运行，无进程退出码。每次结束（含中途终止）**必须**在输出末尾单独打印一行 `状态：{含义}（exitCode={N}）` 供上层判定。

| exitCode | 含义 | 触发场景 | 后续动作 |
|---------|------|---------|-----------|
| 0 | 本段完成 | 完成 STEP 6 并输出段交回信号 | 编排段调用下一段，或用户单独取用技术分册 |
| 1 | 中途终止（可重试） | 用户主动叫停；用户明确拒绝继续回应提问 | 询问用户：继续共创 / 终止 |
| 2 | 输入异常（不可重试） | `slug` 格式非法；`scope` 取值非法；`outputDir` 无法创建；诉求命中「适用与不适用」的不受理判据 | 提示用户修正参数或调整诉求 |
| 3 | 需人工决策 | 关键前提需用户之外的角色或系统才能确定、本次对话内无法闭环 | 交回待确认清单，由用户安排确认 |

### stderr 格式（JSONL，单行）

```jsonl
{"message":"...","detail":"...","hint":"..."}
```

字段约束：
- `message` 必填，自由文本，简洁单行
- `detail` 可选，多行文本（保留原始错误信息）
- `hint` 可选，给用户的修复提示

## 危险信号（Red Flags）

以下可观测信号表明执行出现偏差，出现任一项必须回退修正：

- RF-IBT1: 追问已开始，而本轮追问的字段编号在 fields.md 第一节中不存在
- RF-IBT2: 单轮输出中需用户回答的问题达到 4 个
- RF-IBT3: 出现「你觉得用什么技术好」这类无候选答案的开放式问题
- RF-IBT4: 某一轮输出通篇是问题，找不到一条用户未提过的可能性
- RF-IBT5: 追问记录里出现 `PRD`、`COM`、`MKT`、`GRW`、`OPS` 前缀的字段编号
- RF-IBT6: 分册中出现没有来源等级标注的数值
- RF-IBT7: 依赖项的费用或许可条款没有出处与取证日期，措辞是「据我所知」「一般是免费的」
- RF-IBT8: 用户答「不知道」的字段，在分册里出现了具体数值却未标【缺口】
- RF-IBT9: 分册中模型代填的取值与用户原话混排，读者无法区分来源
- RF-IBT10: 对话中已给出本轮处置分类，其后找不到 `文档：已更新` 行
- RF-IBT11: 输出中出现「第 N 轮」「还剩 N 个问题」「最后一问」这类轮次表述
- RF-IBT12: 分册或对话中出现「不做」「可推进」这类结论态，或出现否决项编号与判定结果
- RF-IBT13: 某字段取值与 `RQ5` 某条硬约束直接冲突，对话中从未回读过该冲突
- RF-IBT14: 台账无产品分区，分册首行下方找不到未锚定声明行
- RF-IBT15: 功能边界表里存在「对应的产品条目」列为空的行

## 反合理化（Anti-Rationalization）

| 借口 | 反驳 |
|------|------|
| "技术上都能实现，难点这一项可以跳过" | 「都能实现」是没试过的另一种说法。把最难那块的输入输出写出来，一半的乐观当场消失。 |
| "依赖的价格我记得是免费的，不用去查" | 免费额度与超额单价决定第一版要不要花钱。记忆里的价格没有出处也没有日期，拿它算现金需求等于猜。 |
| "功能项跟产品条目大致对得上，不用逐条写" | 对不上的那几条就是第一版做完发现走不通的地方。逐条写出来才能与切片对账。 |
| "许可条款禁止商用，这条路直接否掉" | 结论态由裁决段按判定表取值。你在技术段下的结论没有可消解方式也没有复活条件。 |
| "产品方案还没做，我先按常见功能清单假设一个" | 假设的功能清单会被工时算式当成输入。标【缺口】并声明未锚定，账才可复核。 |
