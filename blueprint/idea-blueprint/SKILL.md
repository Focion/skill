# 诉求孵化的编排段（Idea Blueprint）

> [!IMPORTANT] 路径解析基准
> 文档内相对路径引用一律以本 skill 根目录（`SKILL.md` 所在目录）为基准解析。

本段是 blueprint 流水线的**编排段**：还原诉求 → 建立索引与字段台账 → 按段序调用六个共创段 → 交裁决段收束。六个共创段与裁决段各自是独立 skill，本段**只**做还原、调度与收口，方案内容一律由对应段写入自己的分册。段序恒以产品段起头 —— 这东西本身是什么（游戏的策划案、业务的需求方案、内容的选题与规模）不成形之前，其余五段算出来的账没有对应实物。收尾判据是裁决段给出结论态，结论态包含「不做」。提问轮次不设上限，也不向用户宣告。

## 适用与不适用

- ✅ **适用**：用户有一个尚未成形的诉求，且愿意逐轮回应提问 —— 游戏创意、产品或项目立项、副业构想、突发奇想的可行性开局。
- ❌ **不适用**：纯事实查询、单点执行任务、已有完整方案只要求评审 —— 直接回答，**严禁**启动本流程。
- ❌ **不适用**：用户只想推进单独一个方面（只谈商业、只谈技术）—— 改由对应的单段 skill 直接承接，**严禁**为一个方面启动全流程。
- 🚫 **不受理**：诉求的成立以违反法律法规、侵犯他人权益或规避平台风控为必要条件 —— 说明原因后停止，**严禁**输出方案（→ stderr + exitCode=2）。
- 🚫 **不受理**：用户明确表示「别问我，直接给方案」—— 本流程以逐轮共创为前提，必须先说明将连续提问，由用户确认；用户坚持不参与时按 [fields.md 第三节](references/fields.md#三用户拒绝参与时的处置)全程以【模型假设】填充并集中回读。

## 参数

| 参数 | 必填 | 说明 |
|------|------|------|
| `demand` | 是 | 待孵化的原始诉求（自然语言，可以只有一句话） |
| `mode` | 否 | 档位，缺省 `full`；两档差异见 [screen-mode.md 第一节](references/screen-mode.md#一两档差异总览) |
| `outputDir` | 否 | 索引、字段台账与各段分册的输出目录，缺省取当前工作目录 |

## 公共约束

> [强约束] 总纲：只做还原、调度与收口。不替用户拍板，不拿臆测充事实，不代下游段写分册，不越过裁决段给结论。

| # | 约束 | 违反后处理 |
|---|------|-----------|
| BP1 | 还原后的诉求**必须**回读给用户确认后再调用任一下游段，**严禁**在目标与成功判据未被确认前调用 | 停止调度，回到诉求还原并请用户确认 |
| BP2 | 每个问题**必须**按 [co-create.md 第二节](references/co-create.md#二单轮提问的候选生成规则)附模型先行给出的候选答案，**严禁**抛出无候选的开放式问题 | 补齐候选后重发本轮 |
| BP3 | 单轮需用户回答的问题数**必须**不超过 3 个，**严禁**单轮抛出 4 个及以上问题 | 超出的问题移入下一轮后重发本轮 |
| BP4 | 用户给出的每个数值**必须**问明来路并按 [co-create.md 第五节](references/co-create.md#五来源等级)标出来源等级，**严禁**把口述数值直接记为已确认事实 | 补问来路后改标来源等级 |
| BP5 | 未闭环的还原字段**必须**按 [co-create.md 第三节](references/co-create.md#三回答处置四分类)标注后推进，**严禁**停在还原步骤反复追同一字段 | 补标签后进入下一步 |
| BP6 | 索引与字段台账**必须**在调用第一个下游段之前按 [pipeline-contract.md 第二节](references/pipeline-contract.md#二索引与字段台账的建立)建立，**严禁**在台账未建立时调用任一段 | 停止调度，先建立索引与台账 |
| BP7 | 段序**必须**以产品段起头，**严禁**在产品段交回收尾信号前调用其余任一段 | 撤回该次调用，改调产品段 |
| BP8 | 各段分册**必须**由该段 skill 自行写入，**严禁**由本段代写任一分册的方案节 | 删除代写内容，改调对应段 |
| BP9 | 跨段冲突**必须**按 [pipeline-contract.md 第五节](references/pipeline-contract.md#五跨段冲突与回读)回读并请用户择一，**严禁**静默以新值覆盖旧值 | 撤回覆盖，回读冲突后重记 |
| BP10 | 结论态**必须**由裁决段判定，**严禁**在本段自行给出结论态或否决结论 | 删除该结论，改调裁决段 |
| BP11 | `mode=screen` 时**必须**只调用 [screen-mode.md 第二节](references/screen-mode.md#二screen-档调用的段)声明的段，**严禁**调用该节之外的段 | 撤回超档调用，改出快筛结论 |
| BP12 | 每次向用户输出**必须**给出段进度，**严禁**出现提问轮次的编号、上限或剩余次数 | 删除轮次表述，改回段进度 |

## 核心流程

> [强约束] STEP 3~8 任一交互步骤中，用户主动叫停，或用户明确拒绝继续回应提问 → stderr + exitCode=1；`mode=screen` 时 STEP 5~7 的调用范围、结论态与产物形态一律按 [screen-mode.md](references/screen-mode.md) 执行，**严禁**按 `full` 档的全集推进。

### STEP 1：参数校验

按标准校验顺序校验：
- **必填**：`demand`（缺失时不得报错退出，必须先向用户提问「你想把哪个想法、项目或诉求推成落地方案？」，拿到回答后再进入下一步）
- **枚举**：`mode`（`screen` / `full`）
- **创建**：`outputDir`

任一校验失败 → stderr + exitCode=2

### STEP 2：读取共创规范

用 Read 工具完整读取 `references/co-create.md`、`references/fields.md`、`references/pipeline-contract.md`，读完再进入下一步。`mode=screen` 时于 STEP 5 前另读完 [screen-mode.md](references/screen-mode.md)。

### STEP 3：还原诉求与锚定目标

按 [fields.md 第一节](references/fields.md#一诉求还原字段)把 `demand` 还原为该节列出的各字段，逐项给候选后按第二节回读给用户确认（遵循 BP1、BP2、BP3、BP4）。用户否认还原结果即按其更正重写再回读一次；仍缺的字段按 co-create 第三节分类处置（遵循 BP5）。

### STEP 4：建立索引与字段台账

按 [pipeline-contract.md 第二节](references/pipeline-contract.md#二索引与字段台账的建立)建立索引与字段台账，把已确认的还原字段逐项写入台账，再单独一行回显两份文件的绝对路径（遵循 BP6）。

### STEP 5：按段序调用各段

按 [pipeline-contract.md 第一节](references/pipeline-contract.md#一段序与产物清单)的段序逐段调用，一次只调一段（遵循 BP7、BP8）：产品段交回收尾信号后才调下一段；每段调用时把 `demand`、`slug`、`outputDir` 与按当前档位取定的 `scope` 传给该段，该段自行按这两项推导台账路径，其追问、取证、发散与分册写入全部由它自己完成。某段交回的关键前提需用户之外的角色或系统才能确定、本次对话内无法闭环 → stderr + exitCode=3。

### STEP 6：段间收口

每段交回后按 [pipeline-contract.md 第四节](references/pipeline-contract.md#四段进度的输出格式)刷新索引的段进度节并输出段进度（遵循 BP12），按第五节核对该段新写入的取值与台账既有取值有无冲突，命中即回读并请用户择一（遵循 BP9）。

### STEP 7：调用裁决段并回填结论

六段全部交回后调用裁决段，同样传入 `demand`、`slug`、`outputDir` 与 `scope`；裁决段交回结论态后按 [pipeline-contract.md 第三节](references/pipeline-contract.md#三索引骨架)把结论态与触发判据编号回填索引的结论节（遵循 BP10、BP11）。

### STEP 8：回显产物清单

按 [pipeline-contract.md 第六节](references/pipeline-contract.md#六收尾回显与幂等)逐行回显索引、台账与各段分册的绝对路径，缺席的分册标出缺席原因。

## 输出规范

### 产物文件

| 文件 | 条件 | 路径 |
|------|------|------|
| 方案索引 | 必产，还原确认后建立并逐段刷新 | `{outputDir}/blueprint-{slug}.md` |
| 字段台账 | 必产，还原确认后建立并逐段追加 | `{outputDir}/blueprint-{slug}.fields.json` |
| 对话内段进度 | 必产 | 直接输出到对话 |

> [强约束] `{slug}` 由 `demand` 按下列规则机械生成：仅保留字母、数字、中文字符与 `-`；英文字母统一转小写；空格转 `-`；连续 `-` 合并为一个；去除 `/`、换行及其他全部标点；按 Unicode 字符计数超过 30 则截断至 30；结果为空则回退为 `idea`。生成后的 `{slug}` 逐字传给各下游段，**严禁**将 `demand` 原文直接拼入文件名。

```markdown
<!-- ✅ 正确：中文保留，空格转 -，英文转小写，全角标点去除 -->
demand「做一个 Roguelike 小游戏（手机端）」→ blueprint-做一个-roguelike-小游戏手机端.md
<!-- ❌ 错误：原文直接拼入，空格与全角括号进入文件名，产出跨平台不可用的路径 -->
blueprint-做一个 Roguelike 小游戏（手机端）.md
```

### 退出码

本技能在对话模式下运行，无进程退出码。每次结束（含中途终止）**必须**在输出末尾单独打印一行 `状态：{含义}（exitCode={N}）` 供上层判定。

| exitCode | 含义 | 触发场景 | 后续动作 |
|---------|------|---------|-----------|
| 0 | 编排完成（含判为不做） | 完成 STEP 8 并回显全部产物路径 | 读取索引结论态 → 选路线执行或按复活条件重启 |
| 1 | 中途终止（可重试） | 用户主动叫停；用户明确拒绝继续回应提问 | 询问用户：继续共创 / 终止 |
| 2 | 输入异常（不可重试） | `mode` 取值非法；`outputDir` 无法创建；诉求命中「适用与不适用」的不受理判据 | 提示用户修正参数或调整诉求 |
| 3 | 需人工决策 | 某段交回的关键前提需用户之外的角色或系统才能确定 | 交回待确认清单，由用户安排确认 |

### stderr 格式（JSONL，单行）

```jsonl
{"message":"...","detail":"...","hint":"..."}
```

字段约束：
- `message` 必填，自由文本，简洁单行
- `detail` 可选，多行文本（保留原始错误信息）
- `hint` 可选，给用户的修复提示

## 危险信号（Red Flags）

以下可观测信号表明执行出现偏差，出现任一项必须回退修正：

- RF-BP1: 用户尚未确认还原后的目标与成功判据，已出现下游段的调用
- RF-BP2: 还原步骤出现「你觉得应该怎么做」这类无候选答案的开放式问题
- RF-BP3: 单轮输出中需用户回答的问题达到 4 个
- RF-BP4: 台账中出现没有来源等级标注的数值
- RF-BP5: 同一还原字段被连续追问 3 轮以上，仍未标注处置分类
- RF-BP6: 第一个下游段已被调用，`outputDir` 下不存在索引或字段台账
- RF-BP7: 调用记录里出现产品段之外的段，而产品段尚未交回收尾信号
- RF-BP8: 某个分册的方案节由本段写入，该段 skill 从未被调用
- RF-BP9: 同一字段在两个分册里取值不同，索引与台账中找不到冲突记录
- RF-BP10: 索引的结论节出现结论态，而裁决段从未被调用
- RF-BP11: `mode=screen`，调用记录里出现营销段、推广段或实施段
- RF-BP12: 输出中出现「第 N 轮」「还剩 N 个问题」「最后一问」这类轮次表述

## 反合理化（Anti-Rationalization）

| 借口 | 反驳 |
|------|------|
| "用户的诉求已经够清楚了，直接调下游段更快" | 诉求里没有成功判据、没有硬约束，下游段拿不到锚点，六段各自定义一套目标，最后拼不到一起。 |
| "先谈商业和技术更能判断值不值得做，产品段以后再补" | 产品没定，商业算的是空气：定价对着哪个东西收钱、成本算哪几项、工时算几个条目，全取决于这东西到底是什么。 |
| "这个字段我顺手写进商业分册就行，不用调那个段" | 你写进去的取值没有经过该段的字段闭环判据与取证要求，台账里它是空的，裁决段照样算不出账。 |
| "单位经济性明显为负，我直接告诉用户别做了" | 结论态由裁决段按判定表取值。你在编排段下的结论没有算式记录、没有复活条件，用户无法复核也无法重启。 |
| "有几个还原字段用户答不上来，我按常见值填上更完整" | 填上的数字会被六个段当成锚点反复引用。缺口标出来才叫完整，编上去只是好看。 |
