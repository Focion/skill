# 诉求还原字段

本文件为 `idea-blueprint` 编排段提供诉求还原字段清单、还原结果的回读格式与用户拒绝参与时的处置。候选生成规则、处置分类、来源等级与单轮输出格式以 [co-create.md](references/co-create.md) 为唯一来源，本文件**严禁**复述。

本段字段总数为 8，单轮输出的完整度分母**必须**取该数，**严禁**另取。

---

## 一、诉求还原字段

`demand` 在调用任一下游段之前先还原为下列字段，逐项给候选后回读给用户确认。

| 字段 | 要拿到的东西 | 闭环判据 | 追问句式 |
|------|------------|---------|---------|
| `RQ1` | 诉求原话 | 取值型：用户原文被逐字记录 | —（直接取 `demand` 原文，**严禁**改写） |
| `RQ2` | 产物类型 | 枚举型：用户从候选中选定一项 | 你想做出来的是游戏、业务系统、工具、内容、服务、活动还是硬件？ |
| `RQ3` | 服务对象初判 | 取值型：用户确认一个可点名的人群 | 这东西先给谁用？他们的共同身份标签是什么？ |
| `RQ4` | 成功判据 | 取值型：用户给出一个可判定真假的结果句 | 什么结果出现了，你会认为这件事做成了？ |
| `RQ5` | 硬约束 | 枚举型：用户列出不可违反的前提 | 时间、钱、人、技能、合规里，哪些是你现在改不了的？ |
| `RQ6` | 现有资源 | 枚举型：用户列出已有资产 | 你手上已经有什么可以直接用：技能、账号、人脉、素材、代码还是钱？ |
| `RQ7` | 最接近的相关经历 | 取值型：用户给出一件做过的事及其结果 | 你做过的事里，哪一件最接近这个？当时做到什么程度、结果如何？ |
| `RQ8` | 决策人与否决人 | 取值型：用户点明拍板的人 | 这件事最终由谁拍板？除你之外，谁能一句话把它否掉？ |

- `RQ4` 未闭环时**严禁**调用任一下游段 —— 没有成功判据，各段的候选无法排序
- `RQ2` 未闭环时**严禁**调用产品段 —— 产品段按该字段路由到产物类型分册
- `RQ3`、`RQ5`~`RQ8` 未闭环时**必须**按 co-create 第三节分类标注后推进，**严禁**停在本步反复追同一字段
- `RQ8` 指出的拍板人不是用户本人时**必须**在台账中标出该人，**严禁**当作用户自己就能决定
- `RQ5` 的每一条硬约束**必须**逐条写入台账，**严禁**合并成一句 —— 各段要逐条比对它判冲突

**空洞回答与追加问法**：

| 空洞回答 | 追加问法 |
|---------|---------|
| 「就是想做个好玩的东西」 | 做成之后你打算拿它做什么：自己用、给人用、卖钱还是当作品？ |
| 「成功就是做出来」 | 做出来之后哪个具体结果出现了才算成：有人用了、有人付钱了，还是你自己每天在用？ |
| 「没什么限制，都可以」 | 那反过来问：这件事花多少钱、占多少周、需要谁点头，你现在就明确改不了的是哪一项？ |

## 二、还原结果的回读格式

还原字段逐项拿到之后，一次性回读并请用户选出口，格式固定如下。

```markdown
我理解你要做的是 {RQ1 摘要}，做出来的是 {RQ2}，先给 {RQ3} 用。
成功的标准是 {RQ4}；不能碰的前提是 {RQ5 逐条}。
拍板的人是 {RQ8}。出口：A 确认，开始共创 ｜ B 有要改的，我说给你
```

- 回读**必须**在调用第一个下游段之前发出，**严禁**在用户未选出口时开始调度
- 回读**必须**把还原字段收在一次输出内，**严禁**拆成多轮回读
- 【缺口】与【模型假设】项**必须**在回读中逐项点名，**严禁**混在已确认取值里
- 用户选 B → 按其更正改写对应字段，改完**必须**再回读一次
- 回读**严禁**夹带评价性措辞，「这个想法挺不错」这类表述出现即违规

```markdown
<!-- ✅ 正确：逐项摘取值，缺口点名，两个出口都留给用户 -->
我理解你要做的是 {RQ1 摘要}，做出来的是 {RQ2}，先给 {RQ3} 用。
成功的标准是 {RQ4}；不能碰的前提是 {RQ5 逐条}。拍板的人是 {RQ8}。
未闭环：RQ7 相关经历【缺口】。出口：A 确认，开始共创 ｜ B 有要改的，我说给你

<!-- ❌ 错误：夹带评价，且替用户确认了还原结果 -->
你这个想法挺不错的，我理解得差不多了，那我们直接开始吧。
```

## 三、用户拒绝参与时的处置

用户明确表示「别问我，直接给方案」时按下列顺序执行。

| 步骤 | 动作 |
|------|------|
| 1 | 说明本流程以逐轮共创为前提，缺少用户输入的方案会带大量假设 |
| 2 | 用户仍拒绝 → 全部未闭环字段以【模型假设】填充，取值取该字段候选中最保守的一条 |
| 3 | 集中回读一次全部【模型假设】，请用户只改其中他在意的条目 |
| 4 | 用户连回读也拒绝 → 照常调度各段，**必须**在索引开头声明全部前提均为模型假设 |

- 第 2 步的「最保守」判据：候选中所需预算最低、所需人力最少的那一条
- 用户的拒绝**必须**按本节处置，**严禁**当成流程终止理由 —— 终止只由用户主动叫停触发
- 全字段由模型代填时**必须**把该情形一并交给裁决段，**严禁**在编排段自行判为可推进
